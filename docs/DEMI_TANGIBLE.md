# Demi-Tangible books and projectiles

A Demi-Tangible enchanted book can be applied at an anvil to any item, including stackable ammunition and modded weapons that normally refuse enchantments. Existing item components, damage, names and stack counts survive. Ordinary anvil experience/prior-work rules and a one-book material cost still apply. A stack of plain books must be split to one before converting it to an enchanted book. Enchanting-table and Ectchantment Machine eligibility are unchanged.

The specific book application is handled by the supported AnvilUpdateEvent before vanilla rejects a non-enchantable input. Its lowest-priority listener also handles generic canceled-anvil vetoes for this enchantment. Demi-Tangible is forced into the native enchantment component; other enchantments on a mixed book must satisfy normal item support and compatibility rules. Unsupported extra enchantments follow the normal mixed-book behavior and are not granted. Names, prior-work costs, output pickup, level payments and grindstone removal remain native operations. Book application does not add a hidden permanent combat component; existing machine-applied components keep their previous behavior. A mod that replaces the entire anvil menu or overwrites results after this event may require a separate adapter.

Either the firing weapon or ammunition can confer Demi-Tangible to a projectile. Standard arrow weapon/pickup stacks and thrown-item stacks are recognized. ItemStack use, use-on/use-first, release, use-tick and finish-use calls also establish a scoped launch context, so arbitrary modded Projectile subclasses can inherit it even without an arrow weapon field. Bows using the ProjectileWeaponItem ammunition API snapshot selected ammunition before it is consumed or normalized. Loaded crossbows retain their own ammo snapshots rather than inheriting unrelated reserve arrows.

A serialized boolean attachment, `mortal_expansion:demi_tangible_projectile`, stores the captured launch permission, including negative results, on each new projectile. It is server-only and adds no packet or per-projectile tick loop. The context matches the actor and restores previous nested context in `finally`. Damage checks never inspect the owner's newly equipped inventory, and disk loading never re-captures permission from the current owner. Older saved arrows with native enchanted weapon/ammo snapshots remain recognized. Ordinary unenchanted shots stay ineffective against intangible targets. Demons keep their 50% resistance to this weapon damage; unrelated spells keep their existing behavior.

This supports modded launchers/projectiles using normal ItemStack use paths, Projectile ownership, native arrow/thrown-item payloads, and projectile-attributed damage sources. Mods that spawn shots asynchronously with no launch/weapon/ammo information, use non-Projectile bullets, replace item-use dispatch, or report only anonymous damage need explicit integration; no generic implementation can infer their missing firing item safely. An enchanted item held at impact is deliberately not enough.

## Migration and checks

No extra runtime mod is required. Existing enchantment IDs, tags and component records remain valid; missing projectile attachments default to false and older native weapon/ammo snapshots remain readable. The only additional version-sensitive hooks are the focused ItemStack use boundaries because the framework offers no universal projectile-with-firing-stack event. Preserve their scope cleanup, join/load distinction and persistent attachment semantics when updating Minecraft.

GameTests use actual AnvilMenu results and pickup, non-enchantable mod items and custom components, stackable arrows, mixed-book restrictions and canceled-event handling. They fire real bow arrows through ItemStack release, check both weapon and ammunition grants, prevent post-launch weapon swapping from changing permission, round-trip entity saves, and exercise a generic non-arrow Projectile plus actual intangible and Demon damage.
