# Native fading: persistence, rendering and migration

## Data

`mortal_expansion:fading` is a persistent/network-synchronized integer item component. Stored faded values are all integers from 1 through 99; absence means 100%. Previously saved 20/40/60/80 values remain valid. Processing copies the native ItemStack, removes/sets only this component and keeps other components and stack counts. Legacy wrapper decoding remains supported, with recursive wrapped sources rejected.

`mortal_expansion:fading_blocks` is a serialized and framework-synchronized immutable chunk attachment. Keys are local positions `((y & 0xFFF) << 8) | (localZ << 4) | localX` (native BlockPos signed 12-bit Y, independent of dimension minimum height); values are opacity percentages from 1 through 99. Native chunk watch/re-watch sync handles loading and multiplayer. The compact network codec sends position varints plus one opacity byte; decoded entry counts/values are validated. Already-loaded chunks only are queried. Metadata changes mark chunks unsaved. No native block entity NBT or capability is replaced.

`mortal_expansion:fading_entity` carries opacity on native FallingBlockEntity instances through saving, tracking, rendering, landing or item drops. Ordinary falling entities do not allocate this attachment.

The old `fancified_block` item/block/block-entity registry IDs and `Source`/`OriginalState`/`Opacity` save fields stay registered. Their renderer/collision logic remains valid; their drops and reprocessed items use the new component format. Existing stacks and placed decorations do not require eager conversion or scanning.

## Native lifecycle boundaries

Supported NeoForge APIs supply attachments/sync, item components, menus, piston Pre/Post events, tooltip events, chunk unload events and rendering-stage events. Narrow mixins are necessary where no supported per-position opacity callback exists:

- ItemStack use/use-first wraps the complete framework transaction; successful placements commit metadata after cancellation and rollback are resolved. BlockItem placement exposes the actual adjusted target/state and also supports direct native placement calls. Multi-part native placement is captured without modifying its block states.
- LevelChunk state changes clear metadata on replacement while keeping same-block properties. Cauldron forms and copper ageing/waxing are recognized native identity-preserving transitions. A bounded same-tick removal cache lets native loot retain opacity even when removal precedes loot creation.
- BlockState drop results add the component to block-item loot, including native transformations such as stone to cobblestone and wall-sign/cauldron item forms, preserving normal loot/counts and separately spawned container-content drops. The actual native piston resolution is observed after head removal (a Pre-event re-resolution gives incorrect sticky-pull results), transferring each pushed position's opacity; the moving-state finalization keeps it. Falling entity spawn/tick/drop hooks carry opacity through actual physics.
- Client chunk tessellation skips only faded positions. Client solid-render/face queries expose geometry behind them. Native block entity, item and falling-entity render dispatchers receive an opacity-adjusted buffer source; pick-block adds the component to the native result.

During version migration, verify these exact signatures and ordering against the target native/framework sources. In particular, retain placement protection rollback, multi-block scope cleanup in `finally`, pre-removal loot behavior, moving-piston final state, and client-only class isolation. Do not replace the original blocks or block entities to simplify rendering.

## Rendering and performance

Only the faded-position client index is traversed, with frustum rejection, rather than scanning blocks in loaded chunks. Model data, seeded baked quads, native offsets and tint providers use the real level. The material-aware face adapter keeps the existing shared-glass flicker fix. Neighbor faces and visibility-graph solidity account for fading. Native block-entity renderers retain their full behavior, textures, shader and vertex format; cached RenderType adapters enable blending and scale ColorModulator alpha while restoring render state afterward. This also preserves fonts, signs, beds and machine-specific vertex layouts without guessing an atlas.

Chunk metadata reads do not initialize attachments on unrelated chunks. The state-change fast path does not scan stored positions, and same-tick removal bookkeeping is bounded with O(1) per-position operations. Piston resolution is bounded by native push limits. Chunk synchronization invalidates one bounded chunk neighborhood; native chunk/dimension/logout events clean client caches. There is no new server tick loop, chunk loader or per-block proxy ticker. Large translucent installations still have client overdraw and render costs, and repeated updates to a heavily faded chunk sync its attachment snapshot.

Third-party GPU code that ignores the supplied native buffers or alpha cannot be made transparent universally by the generic adapter. Such renderers require explicit compatibility work. Normal chunk-renderer replacements also need testing. These rendering limits do not replace or disable machine gameplay.

## Validation

Headless lifecycle tests exercise real native blocks, inventories/tickers/capabilities, doors/fences/crops, falling/piston movement, cancellation, transitions and data codecs. A temporary, uncommitted client harness rendered native/faded comparison items for stone, Magenta Glass, chests, furnaces, doors, fences, signs, beds, banners and Mortal Expansion machines; all client mixin targets loaded and the client exited normally. The generated comparison image is `run/fading-native-smoke.png` in the development checkout. Actual multiplayer client chunk synchronization and arbitrary third-party renderers still need playtesting.

## Sodium and Iris compatibility

Sodium 0.6.13 bypasses the vanilla BlockRenderDispatcher chunk hook. An optional client-only `@Pseudo` mixin skips faded positions in Sodium's `BlockRenderer.renderModel`, so the separate faded pass is their only baked model. Sodium is not a required dependency. Check this signature when upgrading Sodium.

Standard solid/cutout/translucent entity materials (including chest materials) use the native culled translucent RenderType with per-vertex alpha. This lets Iris classify them as translucent and avoids treating a faded chest as opaque/cutout geometry or drawing its back faces through its front. Three narrow read-only accessors obtain the native material texture without parsing RenderType names or assuming a texture atlas. Other shaders/formats keep the original adapter. Recheck accessor names and shader classifications during Minecraft/Iris upgrades. Redstone remains the native model and tint, rendered once by the faded baked pass.

## Coplanar translucent overlap

The vanilla closed chest lid occupies Y=9..14 model pixels while the body occupies Y=0..10: the side faces overlap by one pixel. Redstone wire multipart models also layer flat quads. Alpha blending exposes their coplanar depth conflict, and normal distance sorting can swap the faces' order as the camera moves.

Faded standard entity materials and faded baked blocks now use a cached native composite translucent material. Faded buffer acquisition marks the native BufferBuilder, and its build result carries that marker to MeshData. A focused MeshData sorting hook applies `FadingOverlap` only to marked meshes. This survives Iris segmented batching (active even when shaders are disabled), which never calls vanilla BufferSource.endBatch. It groups same-facing, axis-aligned coplanar quads whose projected interiors overlap, keeps their original submission order within the normal distance-sorted index order, and gives each layer a small outward depth separation (at most 1/256 block). Touching edges, opposite faces, non-overlapping geometry, ordinary opaque blocks and special shader fallback materials are unchanged. Animation, UVs, tint, lighting, collision and gameplay stay native. This is visual overlap handling, not a replacement model for chests or wire.

Detection uses small spatial/plane buckets with at most 64 candidates stored per cell; only faces at most two blocks wide in each plane direction participate. Arbitrary non-axis-aligned overlaps and very large modded faces remain outside this correction. No world scan, server change or persistent data change is added. During migrations verify BufferBuilder.build and MeshData.sortQuads, the marker transfer, and native composite material/Iris compatibility. Position offset and stride come from the actual mesh VertexFormat; extended Iris layouts are supported without requiring NEW_ENTITY identity. Mesh correction is prepared once to avoid accumulating offsets if a mesh is sorted again.

`tools/client_checks/FadingOverlapCheck.java` is a development-only client check, excluded from normal source sets. Copy it temporarily into the client source package, launch with JVM property `mortal_expansion.overlapCheck=true`, and remove it afterward. It checks moving-camera order, separation bounds, touching-edge/non-overlap preservation, actual vanilla single/double chest and redstone geometry, the real buffer upload hook, and Iris SegmentedBufferBuilder.getSegments with marked geometry. A successful Iris run reports both `FADING_IRIS_BATCH_OK` and `FADING_OVERLAP_CHECK_OK` and exits. Earlier checks that uploaded through vanilla BufferSource did not cover Iris segmented batching; the explicit segmented-batch check closes that gap. An in-world moving-camera playtest remains necessary to confirm the reported visual symptom on the player's shader/GPU setup.

The per-user menu sends selection buttons 1..100 and Apply=0 through the native container-button packet; server-side bounds and access checks remain authoritative. The field and slider share the same whole-number range, and preview items use the real fading component renderer. Item and falling-entity codecs accept the expanded range; existing chunk stream bytes already fit it.

Opacity 1..9 uses a small registered core shader with the native entity vertex shader and fog/lighting uniforms. It tests texture alpha before multiplying selected opacity, avoiding vanilla's final-alpha 0.1 discard threshold. Values 10..99 retain the existing native/Iris translucent shader path. Both material variants keep marked-mesh overlap correction and are flushed after the faded world pass. When migrating, verify RegisterShadersEvent, the referenced native vertex shader, uniforms, and behavior under shader packs; custom low-opacity shaders may use native lighting rather than pack-specific material effects.

`tools/client_checks/FancifierPercentCheck.java` checks all 100 numeric values and invalid text, renders the real screen in a render-only host, and captures the 37%, 1% and 9% previews. Like other client checks, copy it temporarily into the client package, launch with `mortal_expansion.percentCheck=true` and master volume 0.3, then remove it from production sources. The host avoids container ticking without a joined player; gameplay/server behavior is covered separately by GameTests.
